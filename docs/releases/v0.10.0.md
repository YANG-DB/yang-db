# YANG-DB 0.10.0 — faster, consistent cursors, V1 spec

The first release after the 2026 revival's speed work. Queries make far fewer requests to OpenSearch and use less of
the engine's CPU; a query can read one consistent snapshot of the data; V1, the native query format, is published as a
specification; and two V1 bugs that gave wrong or empty answers are fixed. It runs on OpenSearch 2.19.7, and you don't
need to reload or reindex your data.

## Upgrading from 0.9.x

Replace the engine (the Docker image or the distribution) and restart it. Indices, templates and data stay as they are.
Read [changes to note](#changes-to-note) if a client keeps queries for later, if you embed `fuse-core` as a library,
or if you use the API reference or the log configuration.

## Quick start

```bash
cd docker
YANGDB_IMAGE=ghcr.io/yang-db/yang.db YANGDB_TAG=0.10.0 docker compose -f docker-compose-os.yml up -d
```

This starts OpenSearch 2.19.7, OpenSearch Dashboards and YANG-DB with the Dragons sample ontology. Then open the
playground at `http://localhost:8888/dragons/swagger` (one click loads the tutorial data), or follow
`docs/tutorial/sample/dragons/README.md`. To build the image yourself: `git checkout v0.10.0`, then
`./buildDocker.sh Dragons` and the same compose command without the two variables.

Without Docker: unpack the attached distribution, set `opensearch.hosts` and `opensearch.http.port` in
`dragon/config/application.conf` to your OpenSearch 2.19 cluster, and run `dragon/start-fuse-service.sh`.

## What's new

**Speed** (Phase 7 of the roadmap; each change measured before and after, with the same results)
- **A search is a plain request first.** Only a result larger than one page (10,000 hits) continues as a scroll, and
  every scroll is cleared. Before, every search opened a scroll and needed two more requests to finish it: about half
  of all OpenSearch operations.
- **Growing bulks.** A step reads its input in bulks of 1,000 ids that double up to 10,000, so large results need few
  searches while a small first page stays fast (`unipop.bulk.start`, `.multiplier`, `.max`).
- **Less engine CPU per row.** Building each row's text (its id is a hash of it) and the de-duplication key used
  `String.format`, 15–20% of the engine's CPU on large results; the same text is now built directly.

**Consistent cursors (Point in Time), opt-in**
- `opensearch.paging.mode = pit` in `application.conf`, or `"consistent": true` in a cursor request, makes every search
  of a query, on every page, read one snapshot of the data. The default, `scroll`, is unchanged.
- The snapshot is an OpenSearch Point in Time, opened only on the indices the query reads and released when the cursor
  is exhausted, deleted or expires. Each holds one server-side context per shard, and OpenSearch allows 300 per node,
  which is why it isn't on by default.

**V1, the native query format, as a specification** (`docs/spec/v1/`)
- A JSON Schema of the wire format, served at `GET /fuse/query/v1/schema`.
- A rules page for what the schema can't express, every example checked against the engine in CI.
- A compact text form, `POST /fuse/query/v1/print`, e.g. `start (A:Person) all{ {height > 180} | -[:Know]-> (B:Person) }`.

**API reference:** `/swagger` is Swagger UI 5 with an OpenAPI 3.1 description of every route
(`/swagger/openapi.json`), replacing a Swagger 2.0 file that had drifted from the server.

**Docker image:** published for every release at `ghcr.io/yang-db/yang.db`, now on Eclipse Temurin JDK 11 (Ubuntu)
instead of Alpine 3.14.

**Tooling for contributors:** the benchmark (`docker/bench/`), a full-response snapshot check, CI on JDK 17, and every
ignored test giving its reason.

## Fixes

- **V1 `some` (OR) between filters on the same property returned nothing** (Q16): `height < 165 OR height > 182` became
  one empty range. Ranges are now merged only under AND; the same flaw in `must_not` is fixed too.
- **V1 where-by without `joinType` returned an empty response** (Q17); it now follows the operator.
- **Queries were never removed from memory** (Q14): the 5-minute ttl wasn't enforced, so each undeleted large query
  held tens of MB until the engine ran out of heap.
- **Every request failed for up to a minute after the clock stepped back** (A11): request ids no longer depend on a
  monotonic clock.
- **The engine sometimes hung at start-up** (S1, about 1 start in 3 of the Docker image).
- **20 logback errors at every start** (O1).
- **Tests failed against the packaged `fuse-core` jar** (B1).
- All open security alerts: logback 1.5 with SLF4J 2, Guava 33, commons-io, commons-lang3, json-io, org.json, AssertJ,
  json-path.

## Changes to note

- **Idle queries are removed.** A query that isn't used for its ttl (default 5 minutes) is deleted, as the ttl always
  said. A client that comes back to a query later sets `ttl` (milliseconds) when creating it; `0` keeps it until it's
  deleted.
- **`fuse-core` as a library:** the main jar is the plain module jar; the self-contained jar is
  `fuse-core-0.10.0-all.jar`.
- **Java 11 bytecode.** The code is compiled for Java 11 (it already needed 11 at runtime).
- **Logging:** the Elasticsearch log appender is gone from the distributed `logback.xml`; collect the console or the
  `log/` files instead. Console colours no longer use jansi.
- **API reference:** `/swagger/swagger.json` redirects to `/swagger/openapi.json`; jooby-apitool is removed.
- **Request ids** keep the form `FR<number>`, with a new epoch.
- **V1 OR on one property** now returns the matching rows (Q16); a query that relied on the old, empty answer changes.
- **PIT mode and `distinct`:** a query with `distinct` on relationships keeps the first relationship it meets per pair;
  in PIT mode hits arrive in another order, so it can keep a different one of several parallel relationships.

## Known limitations

- **A large CSV fails to load as a whole** (L5): the loader sends a file as one bulk request. Post large files in
  pieces (`docker/e2e/load_tutorial.py` shows how).
- **Cypher `RETURN` doesn't narrow the answer** (Q15): every element of the matched pattern comes back with all its
  properties.
- **V1:** `/v1/validate` checks before rewriting (Q18), `RelUntyped` without `vTypes` drops the relation (Q19), a cycle
  crashes instead of being reported (Q20).
- An exception during a run can come back as HTTP 200 with an empty body instead of an error.
- Running the engine on JDK 17 isn't tested yet (the build and tests are).
- Open issues: `docs/revival/KNOWN_ISSUES.md`. Next: OpenSearch 3.x (Phase 6) and engine-side profiling (ROADMAP 7.12).
