# YANG-DB 0.9.0 — OpenSearch 2.19

YANG-DB now runs on a supported OpenSearch: **2.19.7**. It talks to the cluster over the REST API, so it works with
any OpenSearch 2.19 deployment you can reach over HTTP.

| | |
|---|---|
| OpenSearch | **2.19.7** (Lucene 9.12) |
| Java | 11 |
| Branch | `release/0.9.x` |
| Previous release | [0.8.0](https://github.com/YANG-DB/yang-db/releases/tag/v0.8.0): OpenSearch 1.3, maintained on `release/0.8.x` |
| Download | `yangdb-0.9.0-distribution.tar.gz`, attached below (built from the tag by the Release workflow) |

## Quick start

```bash
git checkout v0.9.0
cd docker
./buildDocker.sh Dragons        # builds the engine and the yangdb/yang.db:Dragons image
docker compose -f docker-compose-os.yml up -d
```

This starts OpenSearch 2.19.7, OpenSearch Dashboards and YANG-DB with the Dragons sample ontology. Then follow
`docs/tutorial/sample/dragons/README.md`, or open the playground at `http://localhost:8888/dragons/swagger`, where
every example query is already filled in. `docker/README.md` has the details.

To run without Docker, unpack the attached distribution, then point it at your OpenSearch 2.19 cluster: in
`dragon/config/application.conf`, set `opensearch.hosts` (the shipped value, `"opensearch"`, is the Docker service
name) and `opensearch.http.port` (default 9200). Then run `dragon/start-fuse-service.sh`. The configuration is read
only from that file: the script's `--opensearch.*` flags have no effect.

## What changed

**OpenSearch 2.19.7**
- Built against OpenSearch 2.19.7 and Lucene 9.12.3. The Docker setup uses the official 2.19.7 images.
- Indices and templates are untyped, since OpenSearch 2.x removed mapping types.
- Dependencies are aligned with 2.19: netty 4.1, Jackson 2.18 and log4j 2.25. Painless runs on ANTLR 4.13.1.
  GraphQL moved to graphql-java 24.3, which bundles its own ANTLR.

**REST connection instead of the transport client**
- OpenSearch 2.x removed `TransportClient`. A new module, `fuse-opensearch-client`, implements the same `Client`
  interface over the REST high-level client. The engine code that uses the client is unchanged.
- The engine connects over HTTP, port 9200 by default. Set `opensearch.http.port` in your configuration. An old
  configuration that only has `opensearch.port = 9300` still works: it maps to 9200 (port − 100) and logs a
  deprecation warning.
- The embedded test node and the statistics client use the same REST connection.

**Fixes found on the live cluster**

Both were found by the Docker end-to-end suite; the embedded-node tests can't catch them. Both have regression tests.
- `init` stopped midway with a NullPointerException, and indices were created without their mappings.
- Count filters returned nothing. On REST, aggregation results arrive as parsed classes, so the engine now reads them
  through the public `Terms` and `Histogram` interfaces.

**Release tooling**
- Every published GitHub release gets a built distribution and its SHA-256 checksum attached automatically
  (`.github/workflows/release.yml`).

**Verified**
- Full build: 1,249 tests, 0 failures.
- Docker end-to-end suite on OpenSearch 2.19.7: all 34 checks pass. These cover every tutorial and playground query
  and the regression set. CI runs the suite on every pull request.

## Upgrading from 0.8.x (OpenSearch 1.3)

OpenSearch 2.19 opens indices written by 1.3 with their data intact. The recommended path is an in-place upgrade:

1. Take a snapshot of the cluster. OpenSearch can't downgrade indices, so the snapshot is your rollback.
2. Stop YANG-DB.
3. Upgrade OpenSearch to 2.19.7.
4. Deploy YANG-DB 0.9.0. Set `opensearch.http.port`, or keep `opensearch.port` (see above).
5. Re-apply the index templates for each ontology with `GET /fuse/load/ontology/{id}/init`. The new templates are
   untyped and only affect indices created from now on.
6. Run your usual queries, or `python3 docker/e2e/doc_queries.py` against the Dragons sample, to check the results.

Other options (reindexing or reloading) and the full list of breaking changes are in
`docs/revival/OPENSEARCH_MIGRATION.md`.

## Performance

Compared with 0.8.0 on OpenSearch 1.3, in a benchmark run after the release ([docs/benchmark.md](../benchmark.md)):
moving to OpenSearch 2.19 and the REST API leaves the OpenSearch work the same (1,359 vs 1,360 shard operations on
the tutorial data) and latency within run-to-run variation, on the tutorial data and on 10 times it.

## Known limitations

- The in-place upgrade was rehearsed after the release (2026-11-23): the tutorial data loaded with 0.8.0 on
  OpenSearch 1.3.0, the cluster was upgraded to 2.19.7, and 0.9.0 returned identical results for every query, without
  reloading. Your own data has not been through that test, so take the snapshot in step 1.
- Open issues are in `docs/revival/KNOWN_ISSUES.md`. Tests that are still ignored, with the reason for each, are in
  `docs/revival/IGNORED_TESTS.md`.
- Next: OpenSearch 3.x on JDK 21 (Phase 6 in `docs/revival/ROADMAP.md`). OpenSearch 3.x only reads indices created on
  2.x, so moving to 2.19 now is the first step there.
